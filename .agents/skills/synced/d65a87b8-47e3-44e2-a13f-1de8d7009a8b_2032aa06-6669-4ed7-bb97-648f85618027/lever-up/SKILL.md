## The Core Philosophy

The calendar IS the system. Not Notion (yet), not a checklist, not good intentions. A recurring calendar event is a forcing function — it makes the behavior happen by putting it in front of you at a specific time. The principle: "Matteo IS fitness." One scheduled commitment forces multiple levers to move. Your job is to find each dimension's "Matteo."

### Step 3: Classify Every Lever
Sort all 49 levers (7 categories x 7 goals) into two categories:

**Appointment-Based Levers** — Need a specific scheduled event (e.g., doctor visits, meetings, sessions):
- Create one-time or recurring calendar events with specific dates
- Include provider info, locations, action items in the description
- Front-load appointments across the year (quarterly cadence is a good default)

**Habit-Based Levers** — Need a forcing function, not an appointment:
- Group related levers into weekly/daily calendar blocks
- Apply the "Matteo Principle": one scheduled block that forces multiple levers to move
- Create rich descriptions that list exactly what to do during the block

### Step 4: Identify Insurance and Prerequisites
- What insurance or access does the user need for this pillar?
- Are there enrollment deadlines, waiting periods, or prerequisites?
- Create "enroll" or "research" events for anything that needs setup before the real appointments can happen

## Event Creation Standards

Every event in this pillar MUST follow these standards:

### Naming Convention
```
[PILLAR#]. [Dimension] | [Lever]: [Action]
```
Examples:
- `1. Medical | PCP: Q2 Checkup + Bloodwork`
- `2. Bills | Subscriptions: Annual Audit`
- `3. Professional | LinkedIn: Weekly Post`
- `6. Consultancy | Pipeline: Q2 Outreach`
- `7. Investing | Keith Meetings: Quarterly Review`

The pillar number prefix ensures events from different pillars are visually distinct on the calendar.

### Required Event Properties
For every event created or updated:
- **summary**: Follow the naming convention above
- **colorId**: Use the pillar's assigned color (see table above)
- **attendees**: ALWAYS include BOTH:
  - `marcellamay21@gmail.com` (the user — organizer)
  - `sf.bay.household@gmail.com` (shared household calendar — Elvis subscribes to this)
- **calendarId**: `marcellamay21@gmail.com` (personal calendar)
- **sendUpdates**: `none` (don't spam with notifications)
- **description**: Rich, actionable — not just a title. Include:
  - What to do (step by step)
  - Why it matters (which levers this covers)
  - Provider info / locations if applicable
  - Emergency contacts if relevant
  - Which dimension this belongs to

### Recurring Event Best Practices
- **Weekly forcing functions**: Use `RRULE:FREQ=WEEKLY` with `COUNT` to scope to rest of year
- **Monthly check-ins**: Use `RRULE:FREQ=MONTHLY` with `BYMONTHDAY=1` or similar
- **Start dates**: ALWAYS start this week or this weekend, never "next month"
- **Updating all occurrences**: Update the parent event ID (no date suffix) to change the whole series

### Event Types to Create

For each pillar, you'll typically need:

1. **Weekly Forcing Function Blocks** (3-5 per pillar)
   - Each block covers an entire dimension through structured activities
   - 15-60 minutes depending on complexity
   - Rich descriptions with numbered steps and lever mapping
   - Example: Sunday Meal Prep (covers all 7 Nutrition levers)

2. **One-Time Appointment Events** (10-20 per pillar)
   - Spread across the year (quarterly cadence)
   - Include action items and prep work in description
   - Front-loaded: earlier appointments come first

3. **Setup/Research Events** (2-5 per pillar)
   - For things that need investigation before scheduling
   - "Enroll in X insurance", "Research Y provider", "Set up Z app"
   - Scheduled in the first 2-4 weeks

4. **Monthly Pillar Review** (1 per pillar)
   - All-day event on the 1st of each month
   - Lists ALL 49 levers as a checklist
   - "What moved? What stalled? What needs scheduling?"

5. **Recovery/Transition Events** (as needed)
   - If the user is recovering from something or transitioning
   - Time-boxed blocks with specific milestone markers

## Common Patterns That Work

These patterns emerged from the Health pillar and apply broadly:

**The Pillar Day**: Each pillar has an assigned day of the week. Use this for the pillar's primary weekly forcing function block. Health = Monday, Systems = Tuesday, Vocation = Wednesday, Finances = Thursday, Core = Friday, Dreams = Saturday, Networking = Sunday. This means the calendar naturally distributes attention across all 7 pillars throughout the week.

**The Matteo Principle**: Find the one scheduled commitment that forces multiple levers to move. Matteo IS fitness — one trainer session covers Strength, Form, Consistency, Recovery. For every dimension, ask: "What is the Matteo here? What one thing, if I show up for it, makes 3-5 other levers move?"

**The Daily Wind-Down**: A nightly 30-min block that covers an entire dimension through routine. Works for Sleep (wind-down protocol), Core (journaling/values check), Networking (check-in text).

**The Quarterly Professional**: PCP every quarter, dentist every quarter, Keith (financial advisor) every quarter, career coach every quarter. Professionals are your forcing functions for dimensions you can't self-serve.

**The Monthly 1st Check-In**: All-day event on the 1st. Lists every lever for that pillar. Takes 10 minutes to scan and catches anything slipping.

**The Research Sprint**: For a new pillar setup, batch all "research and enroll" tasks into the first 2 weeks. Don't let setup tasks linger — give them deadlines.

## Error Prevention

Learn from the Health pillar mistakes:

- **Always check BOTH calendars** (personal and official) when searching for existing events
- **Start recurring events THIS WEEK**, not next month — the user wants action now
- **Always set the color** on creation, not as a follow-up
- **Always include BOTH attendees** (marcellamay21 + sf.bay.household) on creation, not as a follow-up
- **When updating attendees, provide the COMPLETE list** — the API replaces, it doesn't append
- **Use the parent event ID** (no date suffix) to update all occurrences of a recurring event
- **Front-load everything** — if it can happen sooner, schedule it sooner
